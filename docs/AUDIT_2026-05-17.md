## 3. Bugs reales

### 🔴 BUG-1 [BLOQUEANTE — verificado live] — `POST /appointments` ignora `employee_absences`

- **Archivos**: `AppointmentService.java:114-302`, `AppointmentValidator.java:1-246`
- **Detalle**: `AppointmentValidator` tiene 6 métodos públicos (`validateAppointmentInterval`, `validateEmployeeSchedule`, `validateNoOverlap`, `validateNoBoothOverlap`, `validateNoScheduleBlock`, `validateStatusTransition`). **No existe `validateNoEmployeeAbsence`**. Confirmado con grep: `EmployeeAbsence` solo aparece dentro de `modules/appointment` en `AvailabilityService.java`, nunca en `AppointmentService` ni `AppointmentValidator`.
- **Repro live**:
  ```bash
  # 1. Crear absence Maria (membership=3) 2027-03-17 09:00-13:00 → 201 OK
  POST /api/businesses/1/users/3/absences
  {"startDateTime":"2027-03-17T09:00:00","endDateTime":"2027-03-17T13:00:00","reason":"..."}
  → 201

  # 2. GET availability MISMO dia: correctamente no muestra slots 09:00-13:00 para Maria
  GET /api/businesses/1/availability?date=2027-03-17&serviceIds=1&membershipId=3
  → solo slots 15:00+

  # 3. POST cita Maria 10:00 (DENTRO de la absence): NO debería crearse
  POST /api/businesses/1/appointments
  {"clientId":2,"membershipId":3,"serviceIds":[1],"startDateTime":"2027-03-17T10:00:00"}
  → 201 ❌ (cita id=6 creada). Esperado 409 "El empleado tiene una ausencia en ese horario".
  ```
- **Por qué importa**: `GET /availability` es read-only; `POST /appointments` es el camino de la verdad. Un cliente legítimo que use el flujo "consulta huecos → reserva" no triggea el bug, pero cualquier integración directa (script, Postman, importación) lo hace. La ausencia no protege la agenda.
- **Severidad**: **MAYOR**. No es 100% bloqueante para mostrar el frontend, pero sí compromete una promesa funcional del modelo de datos. Fix recomendado antes de defender el TFG.
- **Fix sugerido (~30 min)**:
  1. Añadir a `AppointmentValidator`:
     ```java
     public void validateNoEmployeeAbsence(Long membershipId,
                                            LocalDateTime start,
                                            LocalDateTime end) {
         // existe ya findOverlappingForDayBatch en EmployeeAbsenceRepository;
         // crear findOverlappingByMembershipAndRange o reutilizar
         List<EmployeeAbsence> overlaps = absenceRepository
                 .findOverlappingByMembershipAndRange(membershipId, start, end);
         if (!overlaps.isEmpty()) {
             String reason = overlaps.get(0).getReason();
             throw new ResponseStatusException(HttpStatus.CONFLICT,
                 reason != null ? "El empleado tiene una ausencia: " + reason
                                : "El empleado tiene una ausencia en ese horario");
         }
     }
     ```
  2. Llamarlo en `AppointmentService.createAppointment` entre `validateNoOverlap` (línea 217) y `validateNoBoothOverlap` (línea 247).
  3. Añadir un test unitario.

### 🟡 BUG-2 [MENOR — corner case] — `POST /appointments` ignora `business_hours`

- **Archivos**: `AppointmentService.java:114-302`, `AppointmentValidator.java`
- **Detalle**: la validación se apoya implícitamente en `validateEmployeeSchedule` — si el empleado no tiene `employee_schedules` para el día, falla. Pero si por un error de datos el empleado tiene schedule un día cuando el negocio está cerrado (`business_hours.is_closed = true`), la cita se crearía pese a que el negocio está cerrado.
- **Severidad**: **MENOR**. Con el seed canónico no se manifiesta (employee_schedules están subordinados a business_hours por convención humana, no por constraint). Defensa en profundidad.
- **Fix sugerido**: opcional. Añadir `validateBusinessOpen(businessId, dayOfWeek)` o aceptar que es responsabilidad del ADMIN no crear horarios incoherentes.

### 🟡 GAP-3 [GAP — decisión de diseño] — `markPayment` no chequea estado actual

- **Archivo**: `AppointmentService.java:412-430`
- **Detalle**: `PATCH .../payment` con `{"isPaid": true}` se aplica a cualquier appointment, incluida una `CANCELLED` o `NO_SHOW`. Semánticamente raro ("¿pagaste por una cita cancelada?"). También permite re-aplicar el mismo valor (`isPaid=true` cuando ya era true) rellenando `updatedAt` innecesariamente.
- **Severidad**: **MENOR**. Probable decisión consciente (recepción puede registrar pagos puntuales con cobros previos a cancelación). Si lo prefieres bloquear: añadir guard `if (status in {CANCELLED, NO_SHOW}) throw 400`.

## 7. Formato JSON

Verificado live con smoke + curls.

### 7.1 Respuestas exitosas

- `LoginRequest` → `TokenResponse {token, tokenType, businesses?}` — `tokenType` ∈ {"tenant","identity"}, `businesses` solo en identity.
- `Page<T>` para los listados paginados — Spring por defecto serializa `PageImpl` "as-is" (Spring lo advierte: `Serializing PageImpl instances as-is is not supported, ... use PagedModel`). El frontend deberá pegarse al formato actual (`{content:[...], totalPages, ...}`). Decisión consciente, OK para TFG.
- `BusinessResponse` incluye `latitude` y `longitude` (BigDecimal) si geocoding resolvió; null en otro caso. ✅
- `AppointmentResponse` aplana clientId+clientName, membershipId+userFullName, boothId+boothName, statusId+statusName. Lista de `bookedServices`. `createdAt` y `updatedAt` presentes. ✅

### 7.2 Respuestas de error

Formato uniforme `ErrorResponse {status, error, message, timestamp}` con `error` = `HttpStatus.getReasonPhrase()` RFC ("Bad Request", "Not Found", etc.). Verificado live: 401, 403, 404, 405 (caso DELETE /api/roles devuelve 401 por permitAll solo para GET — correcto, no es bug), 409, 400, 415 (no probado live), 500 (no probado live).

`SecurityConfig` (401/403 desde la cadena), `TenantGuardFilter` (403 cross-tenant), `RateLimitFilter` (429) y `GlobalExceptionHandler` (todas las demás) construyen el mismo `ErrorResponse` con `ObjectMapper` singleton. Coherencia verificada en código.

### 7.3 Pega: smoke etiqueta como bug lo que no lo es

El smoke test imprime "405 metodo no soportado" como expectativa para `DELETE /api/roles` pero el observado es **401**. **No es bug**: `/api/roles` está en `permitAll` sólo para `GET`. Un `DELETE` no autenticado dispara primero el filtro de auth → 401 antes de evaluar method-not-allowed. Esto es el comportamiento estándar de Spring Security. Sólo el label del smoke es engañoso.

## ✅ Cosas que funcionan bien (no son hallazgos pero merecen mención para el TFG)

- **Multi-tenancy**: doble barrera (TenantGuardFilter por URL + `findByIdAndBusinessId` en services). Verificada con `GET /api/businesses/2/clients` → 403.
- **Login en 2 pasos (v16)**: discriminación tenant/identity por presencia del claim `businessId` en JWT, `TenantGuardFilter` distingue identity-only de cross-tenant. Mensajes 403 accionables.
- **Anti-enumeration**: `AuthService.login` 4 caminos de fallo → mismo 401 "Credenciales incorrectas". `PasswordResetService.requestReset` siempre 204. `consumeReset` 3 caminos de fallo (no existe / usado / caducado) → mismo 400. Bien diseñado.
- **Pessimistic locks**: `MembershipRepository.findByIdAndBusinessIdForUpdate` y `BoothRepository.findByIdAndBusinessIdForUpdate` previenen TOCTOU en `createAppointment`.
- **Overlap query**: `existsOverlappingAppointment` filtra correctamente `IN ('PENDING','CONFIRMED','IN_PROGRESS')` excluyendo CANCELLED/COMPLETED/NO_SHOW. Aplicado tanto para empleado como cabina.
- **Precios congelados**: `BookedService` guarda `applied_price` y `applied_tax_percentage` en el momento del booking. Cambios futuros no afectan historial.
- **N+1 resuelto**: `AppointmentResponse.from()` ya no carga repo dentro del DTO; el service hace batch fetch en `searchAppointments`.
- **Geocoding best-effort**: si Nominatim falla, lat/lng quedan null sin propagar excepción.
- **State machine**: tabla `Map.of("PENDING", Set.of("CONFIRMED","CANCELLED"), ...)` con estados finales (COMPLETED, CANCELLED, NO_SHOW) sin transiciones. Estable y predecible.
- **Pagination**: 9 listados paginados, 4 con `List<T>` directo cuando la cardinalidad está acotada por diseño (BusinessHour=7, Role=2, AppointmentStatus=6, EmployeeSchedule=≤14).
- **Validación path params**: `@Validated` + `@Positive` en 17/17 controllers.
- **Error responses uniformes**: `ErrorResponse {status, error, message, timestamp}` desde 4 fuentes (`SecurityConfig`, `TenantGuardFilter`, `RateLimitFilter`, `GlobalExceptionHandler`), todas con `getReasonPhrase()` RFC.
- **Updates con `@PreUpdate`**: Appointment con `updatedAt` que se rellena automáticamente (v19), verificado live.
